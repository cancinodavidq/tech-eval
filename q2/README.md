# RAG Evaluation Pipeline

A production-ready Jupyter notebook that scores Retrieval-Augmented Generation systems on three independent metrics. Built as the deliverable for an AI Architect technical assessment.

```text
RAG sample ──► Context Relevance   (cross-encoder)
            ├─► Answer Faithfulness (LLM judge with atomic claim decomposition)
            └─► Answer Correctness  (semantic similarity + LLM factual judge, composite)
```

The synthetic evaluation dataset is generated by Claude at runtime from a user-supplied domain prompt, with six stress cases designed so the three metrics can fail and pass independently of each other.

```bash

python3.11 -m venv .venv && source .venv/bin/activate

jupyter nbconvert --to notebook --execute --inplace rag_evaluation.ipynb

# Option B — open it interactively in Jupyter:
```

The notebook produces three artifacts:
- `synthetic_dataset.json` — the six stress cases Claude generated
- `evaluation_per_sample.csv` — per-sample DataFrame with all sub-scores and the list of unsupported claims
- `evaluation_summary.json` — aggregate means, pass rate, and configuration metadata

Example outputs from a real run are included in this repo so you can inspect the expected shape without running the pipeline.

## Prerequisites

| Requirement | Why |
|---|---|
| Python 3.11 | `sentence-transformers` and `torch` have stable wheels here; later versions may not yet. |
| An Anthropic API key | Used for dataset generation, claim decomposition, and the two LLM judges. |
| ~200 MB free disk | First run downloads `cross-encoder/ms-marco-MiniLM-L-6-v2` (~80 MB) and `all-MiniLM-L6-v2` (~80 MB) from HuggingFace into your local cache. |
| ~$0.10 in API spend per run | ~30 Claude calls per full pipeline; system prompts are cached via Anthropic prompt caching, so re-runs within 5 minutes cost less. |

Other Python versions (3.10, 3.12, 3.13) likely work but are untested here.

When you run cell 7 (`Synthetic dataset → user input`), it will prompt you for a domain. Press Enter to use the default (financial regulation) or type your own — e.g., *"Medical regulation — FDA approval pathways and clinical trial reporting requirements"* — and Claude will generate the six stress cases for that domain.

## Configuration

All knobs live in cell 4 of the notebook (`Configuration`):

| Parameter | Default | What it controls |
|---|---|---|
| `ANTHROPIC_MODEL` | `claude-sonnet-4-5` | Model for dataset generation, claim decomposition, and both LLM judges. |
| `CROSS_ENCODER_MODEL` | `cross-encoder/ms-marco-MiniLM-L-6-v2` | Cross-encoder for context relevance. |
| `EMBEDDING_MODEL` | `sentence-transformers/all-MiniLM-L6-v2` | Embeddings for the semantic component of correctness. |
| `SEMANTIC_WEIGHT` / `FACTUAL_WEIGHT` | `0.4 / 0.6` | Composite correctness weights. Sum must equal 1.0. Tune per domain — factual > semantic for regulated domains. |
| `FAITHFULNESS_PASS_THRESHOLD` | `0.8` | Threshold for the binary pass/fail signal in the aggregate summary. |

The dataset-generation prompt (cell 8) is also customizable — the meta-prompt enforces the six-case structure; the user's domain prompt feeds into the `DOMAIN:` field.

## What the design buys you

Three architectural decisions are documented in detail in the notebook itself (cell 2, *Design decisions*). The short version:

- **Cross-encoder, not embeddings, for context relevance.** Evaluating an embedding-based retriever with the same (or similar) embedding model is circular — semantic similarity is not informational sufficiency. The cross-encoder is a discriminative reranker repurposed at evaluation time.
- **Claim decomposition, not direct judge, for faithfulness.** A direct judge over the full answer loses diagnostic granularity. Decomposing into atomic claims surfaces *which* part hallucinated, which feeds back into RAG design, not just scoring.
- **Composite semantic + factual for correctness.** Neither signal alone is sufficient. Embeddings miss `"500 contracts"` vs `"500 contracts per day"`; an LLM judge alone is expensive overkill for clear paraphrases. The composite score covers both.

For the trade-offs each metric makes and known limitations, see the notebook's *Discussion of results* section.

## Example results

From a real run on the default financial-regulation domain (full output in `evaluation_per_sample.csv`):

| Case | Context Relevance | Faithfulness | Correctness | Designed to demonstrate |
|---|---|---|---|---|
| Happy path | 0.90 | 0.88 | 0.99 | Baseline — all metrics pass |
| Irrelevant chunks | 0.74 | 0.50 | 0.34 | Topical relevance ≠ informational sufficiency |
| Correct but hallucinated | **0.04** | **0.00** | **0.99** | Faithfulness and correctness are independent |
| Faithful to wrong chunks | 1.00 | 1.00 | **0.57** | Inverse — factual judge catches what semantic similarity misses |
| Partially correct | 0.58 | 0.83 | 0.74 | Score granularity (not just 0 or 1) |
| Generator failure | 1.00 | **0.50** | **0.57** | High-quality retrieval, bad generation |

Notice how the semantic component of correctness stays in `0.86–0.99` across all six cases while the factual component ranges `0.0–1.0` — that's the empirical justification for compositing them.

## Cost and scaling notes

- ~5 Claude calls per sample (1 claim decomposition + ~3 claim judgments + 1 factual judge) plus 1 dataset-generation call. For 6 samples that's ~31 calls total, well under $0.20 on Sonnet 4.5.
- System prompts for the judges are cached via Anthropic prompt caching, so the second-and-later samples within a 5-minute window pay the discounted cached-read rate.
- For >100 samples, parallelize `evaluate_sample()` with a worker pool. Cross-encoder predictions can also be batched across samples for further speedup.
- All LLM calls are wrapped in `try/except`. A single sample failing on one metric records a null score and an error message in that row; the pipeline does not stop.
